## ۱. چرا این PoC قبل از شروع پروژه ساخته شد؟

در سند پروژه، مهم‌ترین معیار پذیرش این است: «عملکرد صحیح کیف پول و دفتر کل» و «اجرای فرایند شارژ با کنترل درخواست‌های تکراری و منقضی‌شده». این دو جمله تا وقتی **قابل اندازه‌گیری** نشوند، فقط ادعا هستند.

بنابراین قبل از انتخاب استک و شروع توسعه، یک نمونه عملی از هسته مالی ساخته و اجرا شد تا ثابت شود:
1. طراحی دفتر کل دوطرفه در این دامنه کار می‌کند.
2. الگوریتم جلوگیری از تکرار و مصرف دوباره کد، در برابر **هم‌زمانی واقعی** مقاوم است.
3. Rules «موجودی منفی نشود» و «مانده کش‌شده = مانده مشتق‌شده» قابل تضمین است.
4. اگر فردا جدول مانده‌ها خراب/گم شود، از دفتر کل قابل بازسازی است.

## ۳. نگاشت این PoC به پیاده‌سازی واقعی (Laravel + PostgreSQL)

| مفهوم در PoC | معادل تولید | نکته اجرایی |
|---|---|---|
| `Money(minor=int)` | `bigint` در ستون‌های `*_minor` + Value Object `Money` در PHP | هیچ `float`/`double`؛ `CHECK (amount_minor > 0)` |
| `Ledger.post()` با قفل سراسری | `DB::transaction()` + قیدهای دیتابیس | `BEGIN; ... COMMIT;` با `SELECT ... FOR UPDATE` روی کیف پول |
| `_by_idempotency` dict | جدول `ledger_journals.idempotency_key UNIQUE` + `idempotency_keys` | در ثبت دیتابیس، خطای `23505` = عملیات تکراری → همان نتیجه قبلی |
| قفل ردیف درخواست شارژ | `UPDATE cashin_requests SET status='COMPLETED' ... WHERE code=? AND status IN ('CREATED','VALIDATED')` و بررسی `affected_rows == 1` | تضمین «یک‌بارمصرف» در سطح موتور دیتابیس، نه در کد اپلیکیشن |
| توازن سند | Trigger دیتابیس: مجموع بدهکار = مجموع بستانکار | سند نامتوازن حتی از مسیر SQL دستی هم ثبت نمی‌شود |
| عدم‌تغییر ردیف‌ها | Trigger: `BEFORE UPDATE OR DELETE ON ledger_entries → RAISE EXCEPTION` | پیش‌شرط حسابرسی و انطباق |
| زنجیره هش | ستون‌های `prev_hash`, `hash` + Job بررسی روزانه | تشخیص دست‌کاری مستقیم در دیتابیس |
| بازسازی مانده‌ها (تست ۷) | Artisan Command `ledger:verify-balances` + `ledger:rebuild-snapshots` | اجرای شبانه + پس از هر بازیابی از بکاپ |
| گزارش تطبیق (تست ۸) | View گزارش + خروجی CSV در پنل مدیریت | تطبیق با اظهارنامه صرافی در ماژول `Settlement` |
| قفل سراسری Python | قفل‌های دقیق‌تر: ردیف کیف پول، `pg_advisory_xact_lock` برای عملیات کلان | ترتیب ثابت قفل‌ها برای پرهیز از Deadlock |
| Thread در یک پروسه | تست هم‌زمانی چندپروسه‌ای روی PostgreSQL واقعی در CI | این تفاوت مهم است و باید در ماه ۲ با تست واقعی دیتابیس پوشش داده شود |

### نمونه پیاده‌سازی (اسکلت Laravel) — تأیید شارژ به‌صورت اتمیک

```php
final class ConfirmCashInHandler
{
    public function __construct(
        private LedgerPostingService $ledger,
        private LimitPolicyService $limits,
    ) {}

    public function handle(ConfirmCashInCommand $cmd): CashInReceipt
    {
        return DB::transaction(function () use ($cmd) {
            // ۱) قفل ردیف درخواست شارژ (به‌ترتیب ثابت قفل‌ها)
            $request = CashInRequest::where('code', $cmd->code)->lockForUpdate()->firstOrFail();

            // ۲) اپراتور/صرافی مجاز؟
            $this->limits->assertOperatorAllowed($cmd->operatorId, $request);

            // ۳) گذار وضعیت یک‌بارمصرف — تضمین در سطح دیتابیس
            $affected = DB::update(
                "UPDATE cashin_requests SET status='COMPLETED', operator_id=?, completed_at=now()
                 WHERE id=? AND status IN ('CREATED','VALIDATED') AND expires_at > now()",
                [$cmd->operatorId, $request->id]
            );
            if ($affected !== 1) {
                throw new InvalidCashInState('درخواست قبلاً مصرف یا منقضی شده است.');
            }

            // ۴) سند دفتر کل (idempotent با ایندکس یکتایی)
            $journal = $this->ledger->post(
                type: JournalType::CASHIN,
                idempotencyKey: "cashin:{$request->code}:confirm",
                reference: new Reference('CASHIN_REQUEST', $request->code),
                lines: [
                    Entry::debit($request->partnerAssetAccount(), $request->amount_minor),
                    Entry::credit($request->walletAccount(), $request->net_amount_minor),
                    Entry::credit(Accounts::feeIncome(), $request->fee_minor),
                ],
            );

            // ۵) مانده کش‌شده با قفل ردیف کیف پول
            Wallet::whereKey($request->wallet_id)->lockForUpdate()->increment('balance_minor', $request->net_amount_minor);

            // ۶) Outbox برای پیامک/Push/WebSocket — بیرون از تراکنش اجرا می‌شود
            Outbox::record(new CashInCompleted($journal->id, $request->id));

            return CashInReceipt::from($journal, $request);
        }, attempts: 3);
    }
}
```

> نکته رهبری فنی: **بازبینی این فایل باید اختیار CTO باشد.** در سیستم مالی، خطای یک خط در این‌جا معادل چند ماه کار تیم عملیات برای رفع مغایرت است.

## ۴. آنچه این PoC اثبات *نمی‌کند* (شفاف و بی‌اغراق)

| محدودیت | چطور پوشش داده می‌شود |
|---|---|
| هم‌زمانی چندپروسه‌ای روی PostgreSQL واقعی و رفتار قفل‌ها/Deadlock | تست‌های یکپارچه با دیتابیس واقعی + تست بار (k6) در ماه ۲ و ۳ |
| پیامد Transaction Isolation و Retry در خطاهای `40001/40P01` | تست تزریق خرابی + کد Retry در `Application` لایه |
| نبود آزمون عملکرد (TPS) | هدف پایلوت: ۱۰۰ تراکنش/ثانیه، p95 < ۴۰۰ms — سنجش در ماه ۶ |
| صحت مسیرهای بیرونی (SMS، سامانه گیرنده، بانک) | تست با Stub + محیط Staging + تست پذیرش عملیاتی |
| مدل حقوقی/مجوزی «کیف پول» | خارج از حیطه کد؛ باید با مشاور حقوقی تأیید شود |

## ۵. جمع‌بندی

- سه تضمینی که معماری AZIZIPAY روی آن بنا می‌شود **به‌صورت عملی اثبات شد**: اتمی‌بودن، غیرقابل‌تکرار بودن، توازن همیشگی دفتر کل.
- الگوی «یک‌بارمصرف‌بودن کد + Idempotency + قید یکتایی دیتابیس» در برابر پیک هم‌زمانی مقاوم است؛ این‌ها همان چیزهایی هستند که در سند پروژه برای «جلوگیری از شارژ مضاعف» خواسته شده است.
- این PoC، مبنای تصمیم استک (سند ۳) و نقشه ماه ۱ است: ماژول `Ledger` به‌عنوان مرجع، از روز اول با تست‌های Idempotency و هم‌زمانی در CI.
